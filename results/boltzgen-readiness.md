## Peptides 12–16 residues and cyclization

The official YAML examples support variable design lengths and fixed residues in a protein/peptide `sequence` field. A two-Cys design is shown as `sequence: 10..14C6C3`, and covalent bonds are expressed by atom endpoints, for example:

```yaml
constraints:
  - bond:
      atom1: [S, 11, SG]
      atom2: [S, 18, SG]
```

This is sufficient to encode a disulfide-connected peptide scaffold, including a 12–16-residue design range, if the residue numbering and atom endpoints are correct. The documented `peptide-anything` protocol is the relevant protocol; its README says cysteine is avoided during inverse folding by default, so a disulfide design must explicitly permit cysteine (the captured docs say to pass an empty avoid list when cysteine must be generated). The docs also state that cyclic peptides with various cyclizations are supported, but they do not establish that every noncanonical bridge or terminal chemistry is generated by the sequence designer.

## Pocket contacts and KRpep-2d target preservation

The YAML language supports a target loaded from a `.cif`/`.pdb` file, `include` selections by chain and residue index, and `binding_types` with `binding`/`not_binding` residue ranges. Therefore a KRAS-GDP structure can be targeted around a declared pocket by including the KRAS chain and marking the desired pocket residues as binding. This is a spatial contact bias, not an exact contact guarantee.

The design specification also accepts non-designed molecular entities at atomic level and covalent bond constraints. A target mmCIF that explicitly contains GDP and KRpep-2d with its Cys5–Cys15 disulfide, N-terminal acetyl group, and C-terminal amide can therefore be preserved as an input structure for scoring/design, provided the file’s atom/residue naming is accepted by the parser. The captured official docs do **not** show a direct YAML keyword for acetylation, amidation, or a KRpep-2d-specific residue template. Do not claim that a plain sequence field alone preserves those caps.

## CLI budget controls

The documented controls are:

```bash
boltzgen run peptide_design.yaml \
  --protocol peptide-anything \
  --num_designs 60 \
  --budget 16 \
  --output workbench/krpep2d
```

`--num_designs` is the total/intermediate designs generated; `--budget` is the final diversity-optimized set. The README says practical runs commonly use 10,000–60,000 designs, so `60` is a smoke-scale budget only. The official captured CLI option list included `--num_designs`, `--budget`, `--alpha`, `--inverse_fold_num_sequences`, `--steps`, `--reuse`, and filtering/configuration controls. It did **not** list `num_batches` or a generic `sampling` option. Do not add those flags without checking the exact installed CLI help for the pinned commit.

## Boltz-2 downstream decision

BoltzGen’s official paper/README says BoltzGen unifies design and structure prediction and that input molecular entities include atom positions, elements, charge, post-translational modifications, and covalent bonds. This supports a downstream workflow in which the exact GDP–KRAS–KRpep-2d complex is supplied as an explicit structure file and candidate designs are refolded/scored against that preserved target. It does not, from the captured official sources, prove a Boltz-2 YAML syntax for terminal caps or prove that a generated design retains KRpep-2d chemistry after serialization. Treat the exact caps/disulfide as a **structure-file preservation requirement** and validate the emitted mmCIF before any downstream Boltz-2 run.

## Remaining risks

- The source page and Context7 index are time-sensitive; the commit and version above are the exact values captured on 2026-09-14, not an unverified future release.
- `binding_types` biases contacts to residue ranges; it cannot guarantee a particular hydrogen-bond or salt-bridge network.
- A 12–16-residue peptide range is representable, but exact lower/upper sampling syntax and residue numbering must be checked with `boltzgen check` after installation.
- Terminal acetyl/amidation and exact KRpep-2d disulfide chemistry are not demonstrated as direct YAML sequence features in the captured docs; use an explicit target mmCIF and inspect parser/output artifacts.
- No installation, model download, GPU run, or design generation was performed.

## Pinned-source inspection

The official repository was shallow-cloned into `.tools/boltzgen` without installing its package or weights. `git rev-parse HEAD` matched **`a3149cf18eeb58648d1abbb27539bd73f746cdda`** exactly. Source inspection confirms:

- Backbone cyclization is the YAML key `cyclic: true` under a designed `protein` entity. The official example `example/cylcic_against_kras_with_specific_site/cyclicdesign.yaml` uses `sequence: 8..16` plus `cyclic: true`.
- Disulfides use `constraints`/`bond` atom endpoints, e.g. `[C, 2, SG]` to `[C, 9, SG]` in `example/streptavidin_partially_flexible_target/disulfide.yaml`.
- `boltzgen check` is a real CLI subcommand (`build_check_parser` in `src/boltzgen/cli/boltzgen.py`) that parses a design spec and can emit an annotated mmCIF. It was not executed because dependencies were not installed.
- The parser’s allowed YAML keys include `cyclic`, `constraints`, `bond`, `atom1`, `atom2`, `bondtype`, `ccd`, and `smiles`, but **do not include `modifications`** in its `yaml_keys` validation list even though nearby code reads a `modifications` field. Therefore direct YAML terminal-cap encoding is not a verified supported path at this commit.
- CLI source exposes `--num_designs`, `--diffusion_batch_size`, `--budget`, `--inverse_fold_num_sequences`, and `--inverse_fold_avoid`; there is no `--num_batches` or generic `--sampling` option. `--diffusion_batch_size` controls samples per trunk run and is the source-level equivalent relevant to batching.

The provisional spec is [analysis/boltzgen-pocket.yaml](../analysis/boltzgen-pocket.yaml). It requests a 12–16-residue backbone-cyclic peptide, uses `--num_designs 60` at execution time, includes target chain A and GDP chain C from `results/target/5xco-reference.cif`, and excludes chain B containing the known bound KRpep-2d. Binding residues are the crystal-pocket neighborhood A61, A68, A69, A72, A96, A99, A102, and A103. The YAML is intentionally provisional until `boltzgen check` is run in an installed environment; no validity or compute claim is made here.

## Modal preparation

The preparation wrapper is [analysis/modal_boltzgen.py](../analysis/modal_boltzgen.py). It pins the source checkout above into the Modal image, uses CUDA 12.6 with `torch==2.8.0` from the CUDA 12.6 wheel index and the repository’s cu12 equivariance dependencies, requests one A100-80GB container with CPU 4, memory 16,384 MiB, timeout 3,600 s, startup timeout 300 s, and retries 0. It uses no persistent Modal volume. The function accepts `num_designs` but enforces a hard maximum of 60; the intended first call is `num_designs=2`, followed by a separately reviewed call up to 60.

The wrapper runs `boltzgen --version`, `boltzgen run --help`, `boltzgen check --help`, `boltzgen check`, and then the complete built-in `peptide-anything` pipeline with `--diffusion_batch_size 1`, `--devices 1`, `--num_workers 1`, and an empty `--inverse_fold_avoid` so cysteine is not silently excluded. It captures stdout/stderr, writes run metadata, and returns a tarball of the full output/log directory even when a subprocess fails. It performs no run during preparation.

The CUDA/Torch pairing is a preparation choice guided by the pinned repository Dockerfile’s CUDA 12.2/cu12 setup; it is not yet runtime-verified. If image build or the first remote `boltzgen check` reveals a wheel/driver incompatibility, stop and adjust the image pins before any 60-design call. The target YAML excludes known peptide chain B and includes only KRAS chain A plus GDP chain C.
